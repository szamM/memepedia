
# План тестирования Memepedia

## 1. Общая информация

- Проект: Memepedia
- Версия: v0.1.0
- Ответственный: QA Engineer
- Задача: MEM-8
- Документ: Test Plan
- Статус: На проверке

## 2. Цель тестирования

Цель тестирования — проверить соответствие
веб-платформы Memepedia функциональным
и нефункциональным требованиям.

Основные задачи:
- Выявить дефекты пользовательских сценариев.
- Проверить обработку некорректных данных.
- Оценить корректность отображения интерфейса.
- Проверить взаимодействие компонентов системы.
- Подготовить основу для регрессионного тестирования.

## 3. Объект тестирования

Веб-платформа Memepedia предназначена
для публикации, просмотра и обсуждения мемов.

Проверяемые функциональные модули:

1. Регистрация пользователей.
2. Авторизация и выход из системы.
3. Главная страница и лента мемов.
4. Поиск публикаций.
5. Создание публикаций.
6. Просмотр отдельных мемов.
7. Комментирование.
8. Оценка публикаций.
9. Профиль пользователя.

## 4. Область тестирования

### Включено в план

- Проверка основных функциональных требований.
- Позитивные и негативные сценарии.
- Проверка валидации полей.
- Проверка отображения элементов интерфейса.
- Адаптивность основных страниц.
- Регрессионная проверка после исправления ошибок.

### Не включено в текущий этап

- Полноценное нагрузочное тестирование.
- Аудит информационной безопасности.
- Тестирование мобильного приложения.
- Проверка сторонних платёжных систем.

## 5. Виды тестирования

### Функциональное тестирование

Проверка корректности основных функций
системы и пользовательских сценариев.

### Интеграционное тестирование

Проверка взаимодействия Frontend, Backend
и базы данных после их реализации.

### Регрессионное тестирование

Повторная проверка ранее реализованных
функций после изменений.

### UI-тестирование

Проверка визуального оформления,
расположения компонентов и адаптивности.

### Негативное тестирование

Проверка некорректных входных данных,
ошибочных действий и отказов системы.

## 6. Методы проектирования тестов

- Эквивалентное разбиение (EP).
- Анализ граничных значений (BVA).
- Таблицы принятия решений.
- Тестирование переходов состояний.
- Проверка пользовательских сценариев.
- Исследовательское тестирование.

## 7. Тестовое окружение

### Операционные системы

- macOS

### Браузеры

- Google Chrome

## 8. Тестовые данные

Предусматриваются следующие категории данных:

- Корректные данные регистрации.
- Некорректные email-адреса.
- Пустые обязательные поля.
- Существующие и несуществующие логины.
- Допустимые изображения.
- Недопустимые типы файлов.
- Пустые и заполненные комментарии.
- Существующие и отсутствующие мемы.

Конкретные значения тестовых данных
уточняются перед выполнением проверок.

## 9. Критерии начала тестирования

Тестирование начинается при выполнении
следующих условий:

1. Проверяемая функция реализована.
2. Приложение доступно для запуска.
3. Подготовлены тестовые данные.
4. Описаны ожидаемые результаты.
5. Подготовлено необходимое окружение.

## 10. Критерии завершения тестирования

Тестирование этапа считается завершённым,
если:

1. Выполнены запланированные проверки.
2. Результаты тестов зафиксированы.
3. Обнаруженные дефекты зарегистрированы.
4. Отсутствуют открытые блокирующие дефекты.
5. Подготовлен итоговый отчёт о тестировании.

## 11. Классификация дефектов

### Critical

Блокирует выполнение ключевого сценария
или делает систему недоступной.

### Major

Нарушает важную функциональность приложения.

### Normal

Влияет на работу функции, но имеется
возможный обходной путь.

### Minor

Незначительная ошибка интерфейса
или второстепенной функциональности.

## 12. Управление дефектами

Жизненный цикл дефекта:

1. Обнаружение ошибки.
2. Создание задачи об ошибке.
3. Передача разработчику.
4. Исправление ошибки.
5. Повторная проверка.
6. Закрытие дефекта.

Учёт задач ведётся в YouTrack,
а изменения исходного кода — в GitHub.

## 13. Результаты этапа

Планируемые результаты:

- Подготовленный тест-план.
- Набор функциональных тест-кейсов.
- Определённые критерии приёмки.
- Согласованная стратегия тестирования.
