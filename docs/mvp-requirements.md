
# Требования к MVP Memepedia

## 1. Общая информация

Проект: Memepedia

Спринт: Sprint 2 — MVP Development

Задача: MEM-11

Ответственный: Project Manager

Статус документа: На проверке

## 2. Цель MVP

Цель MVP — предоставить пользователям
базовую работающую версию платформы Memepedia.

В рамках второго спринта необходимо
дополнить существующую главную страницу
системой регистрации и авторизации.

## 3. Пользовательские роли

### Гость

Может:
- Просматривать главную страницу.
- Просматривать публичные мемы.
- Выполнять поиск.
- Переходить на страницы регистрации и входа.

### Авторизованный пользователь

Дополнительно может:
- Входить в свою учётную запись.
- Выходить из учётной записи.
- Просматривать сведения о своём аккаунте.

### Администратор

Обладает правами авторизованного пользователя.

Функции модерации будут реализованы
на следующих этапах проекта.

## 4. Функциональные требования

### FR-MVP-01. Регистрация пользователя

Система должна позволять пользователю
создать учётную запись.

Обязательные поля:
- Имя пользователя.
- Email.
- Пароль.

Требования:
- Email должен иметь корректный формат.
- Email должен быть уникальным.
- Имя пользователя должно быть уникальным.
- Пароль должен содержать не менее 8 символов.
- Обязательные поля не могут быть пустыми.

### FR-MVP-02. Авторизация пользователя

Система должна позволять зарегистрированному
пользователю войти в свою учётную запись.

Для входа используются:
- Email.
- Пароль.

При неверных данных система должна
отображать сообщение об ошибке.

### FR-MVP-03. Выход из системы

Авторизованный пользователь должен
иметь возможность завершить свою сессию.

После выхода защищённые разделы
не должны оставаться доступными.

### FR-MVP-04. Проверка текущего пользователя

Система должна определять,
авторизован ли текущий пользователь.

При наличии активной сессии
должны быть доступны его основные данные.

### FR-MVP-05. Главная страница

На главной странице должны отображаться:
- Название Memepedia.
- Поисковая строка.
- Список карточек мемов.
- Кнопки входа и регистрации для гостей.
- Информация об аккаунте для авторизованных.

### FR-MVP-06. Обработка ошибок

Система должна корректно обрабатывать:
- Некорректный email.
- Пустые обязательные поля.
- Слишком короткий пароль.
- Уже зарегистрированный email.
- Неверный пароль при входе.
- Ошибки соединения с сервером.

## 5. Нефункциональные требования

### Удобство использования

- Формы должны содержать понятные подписи.
- Ошибки должны отображаться рядом с полями.
- Интерфейс должен быть адаптивным.
- Кнопки должны иметь состояния загрузки.

### Безопасность

- Пароли нельзя хранить в открытом виде.
- Передача учётных данных должна
  осуществляться по HTTPS в production.
- Сервер должен проверять входные данные.
- Ошибки входа не должны раскрывать пароль.
- Доступ к защищённым ресурсам
  должен проверяться на сервере.

### Надёжность

- Приложение должно обрабатывать
  недоступность сервера.
- Ошибка запроса не должна приводить
  к аварийному завершению интерфейса.

## 9. Предварительный контракт REST API

Все маршруты API начинаются с /api.

### POST /api/auth/register

Назначение:
Регистрация нового пользователя.

Пример запроса:

```json
{
  "username": "test_user",
  "email": "test@example.com",
  "password": "Password123"
}
```

Успешный ответ:
HTTP 201 Created

```json
{
  "id": 1,
  "username": "test_user",
  "email": "test@example.com"
}
```

Возможные ошибки:
- 400 — некорректные данные.
- 409 — пользователь уже существует.

### POST /api/auth/login

Назначение:
Авторизация пользователя.

Пример запроса:

```json
{
  "email": "test@example.com",
  "password": "Password123"
}
```

Успешный ответ:
HTTP 200 OK

```json
{
  "id": 1,
  "username": "test_user",
  "email": "test@example.com"
}
```

При неверных данных:
HTTP 401 Unauthorized.

### GET /api/auth/me

Назначение:
Получение информации о текущем пользователе.

Успешный ответ:
HTTP 200 OK.

Если пользователь не авторизован:
HTTP 401 Unauthorized.

### POST /api/auth/logout

Назначение:
Завершение пользовательской сессии.

Успешный ответ:
HTTP 204 No Content.

## 10. Управление сессией

В рамках MVP предполагается
использование серверной сессии
с cookie HttpOnly.

Frontend не должен получать пароль
или хранить его в локальном хранилище.

В production необходимо использовать
HTTPS и защищённые параметры cookie.

Точная реализация сессии уточняется
на этапе Backend-разработки.

## 11. Критерии приёмки MVP

### AC-01. Успешная регистрация

Дано:
Гость открыл страницу регистрации.

Когда:
Он вводит корректные данные.

Тогда:
Создаётся новая учётная запись,
а система показывает успешный результат.

### AC-02. Повторный email

Дано:
Email уже зарегистрирован.

Когда:
Гость пытается зарегистрироваться
с этим же email.

Тогда:
Система отклоняет регистрацию.

### AC-03. Успешный вход

Дано:
Пользователь существует в системе.

Когда:
Он вводит правильные учётные данные.

Тогда:
Система создаёт пользовательскую сессию.

### AC-04. Неверный пароль

Дано:
Пользователь существует.

Когда:
Он вводит неправильный пароль.

Тогда:
Система возвращает ошибку авторизации.

### AC-05. Выход

Дано:
Пользователь авторизован.

Когда:
Он нажимает кнопку выхода.

Тогда:
Сессия завершается.

### AC-06. Защищённый ресурс

Дано:
Пользователь не авторизован.

Когда:
Он запрашивает данные текущего аккаунта.

Тогда:
Система возвращает HTTP 401.
